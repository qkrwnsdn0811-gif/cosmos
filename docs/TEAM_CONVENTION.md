# 팀 협업 규칙

이 문서는 프로젝트 구성원이 동일한 기준으로 협업하기 위한 규칙을 정의한다. 모든 팀원은 작업을 시작하기 전에 본 문서를 확인하며, 규칙 변경이 필요한 경우 팀원 간 합의 후 문서를 함께 수정한다.

## 1. 협업 규칙

### 1.1 기본 원칙

- 모든 작업은 이슈 또는 작업 항목을 기준으로 진행한다.
- 작업을 시작하기 전에 담당자와 작업 범위를 명확히 한다.
- 하나의 브랜치에서는 하나의 목적만 다룬다.
- 다른 팀원의 작업과 충돌할 가능성이 있으면 작업 전에 공유한다.
- 기능 변경 시 관련 문서, 테스트 코드 및 설정도 함께 갱신한다.
- 비밀번호, API 키, 인증서 등 민감 정보는 저장소에 올리지 않는다.
- 이해하기 어려운 구현에는 필요한 수준의 설명을 남기되, 코드만 반복해서 설명하는 주석은 지양한다.
- 작업 중 발생한 주요 결정, 문제 및 해결 방법은 팀이 확인할 수 있는 채널에 공유한다.

### 1.2 작업 흐름

1. 이슈 또는 작업 항목을 생성하고 담당자를 지정한다.
2. 최신 `dev` 브랜치를 기준으로 작업 브랜치를 생성한다.
3. 기능 구현과 로컬 검증을 진행한다.
4. 커밋 규칙에 맞게 변경 사항을 커밋한다.
5. 원격 저장소에 브랜치를 Push하고 `dev` 브랜치를 대상으로 Merge Request를 생성한다.
6. 리뷰 의견을 반영하고 필요한 검증을 완료한다.
7. 승인 후 Merge한다.
8. Merge가 완료된 작업 브랜치는 로컬과 원격 저장소에서 정리한다.

단, 코드나 설정에 영향을 주지 않는 간단한 문서 작업은 별도의 작업 브랜치와 Merge Request 없이 `dev`에 직접 반영할 수 있다. 세부 기준은 Push 규칙을 따른다.

## 2. 브랜치 전략

본 프로젝트는 `master`, `dev`, 작업 브랜치로 구성된 단순화된 Git Flow를 사용한다.

| 브랜치 | 목적 | 직접 Push |
| --- | --- | --- |
| `master` | 배포 또는 시연 가능한 안정 버전 관리 | 금지 |
| `dev` | 개발 완료 기능을 통합하고 다음 배포를 준비 | 원칙적 금지(간단한 문서 작업 제외) |
| `feature/*` | 신규 기능 개발 | 허용 |
| `fix/*` | 개발 중 발견된 버그 수정 | 허용 |
| `hotfix/*` | `master`의 긴급 오류 수정 | 허용 |
| `refactor/*` | 동작 변경 없는 코드 구조 개선 | 허용 |
| `docs/*` | 문서 추가 및 수정 | 허용 |
| `chore/*` | 설정, 의존성, 빌드 등 기타 작업 | 허용 |
| `test/*` | 테스트 추가 및 수정 | 허용 |

### 2.1 브랜치 운영 기준

- 일반 작업 브랜치는 최신 `dev`에서 생성한다.
- 일반 작업의 Merge Request 대상 브랜치는 `dev`로 지정한다.
- `master` 반영은 배포 또는 시연 버전이 확정된 경우에만 `dev`에서 Merge Request를 생성하여 진행한다.
- 긴급 수정이 필요한 경우에만 `master`에서 `hotfix/*` 브랜치를 생성한다. 수정 완료 후 `master`와 `dev` 모두에 반영하여 변경 사항이 누락되지 않도록 한다.
- `master`와 `dev`에는 원칙적으로 직접 Commit 또는 Push하지 않는다.
- 단, 코드나 설정에 영향을 주지 않는 간단한 문서 작업은 팀에 공유한 뒤 `dev`에 직접 Commit 및 Push할 수 있다.
- 공용 브랜치의 커밋 이력을 임의로 변경하지 않는다.
- 장기간 유지되는 작업 브랜치는 주기적으로 `dev`의 변경 사항을 반영하여 충돌을 최소화한다.

## 3. 브랜치 이름 규칙

### 3.1 형식

```text
<type>/<issue-key>-<short-description>
```

- `type`은 소문자로 작성한다.
- `issue-key`는 Jira 또는 GitLab 이슈 식별자를 사용한다.
- `short-description`은 작업 내용을 알 수 있는 짧은 영문 소문자로 작성한다.
- 단어 구분에는 하이픈(`-`)을 사용한다.
- 공백, 한글, 밑줄 및 불필요한 특수문자는 사용하지 않는다.

### 3.2 예시

```text
feature/S15P21C205-12-company-search
fix/S15P21C205-24-graph-rendering
docs/S15P21C205-31-team-convention
refactor/S15P21C205-38-news-parser
```

이슈가 없는 단순 작업은 팀과 공유한 뒤 이슈 식별자를 생략할 수 있다.

```text
chore/update-dependencies
```

## 4. 커밋 메시지 규칙

### 4.1 형식

```text
<type>(<issue-key>): <subject>
```

Jira 이슈 키를 커밋 메시지의 범위(scope) 위치에 작성하여 GitLab의 개발 활동이 Jira 이슈에 연결되도록 한다.

필요한 경우 본문을 추가한다.

```text
<type>(<issue-key>): <subject>

<body>
```

Jira 이슈가 없는 단순 작업은 팀에 작업 내용을 공유한 뒤 이슈 키를 생략할 수 있다.

```text
<type>: <subject>
```

간단한 문서 작업이라도 관련 Jira 이슈가 존재하면 이슈 키를 생략하지 않는다.

```text
docs(S15P21C205-31): 팀 협업 규칙 문서 작성
```

### 4.2 커밋 타입

| 타입 | 설명 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가 또는 수정 |
| `style` | 포맷, 공백 등 동작에 영향을 주지 않는 변경 |
| `refactor` | 기능 변경 없는 코드 구조 개선 |
| `test` | 테스트 코드 추가 또는 수정 |
| `chore` | 설정, 의존성, 빌드 등 기타 작업 |
| `perf` | 성능 개선 |
| `ci` | CI/CD 설정 변경 |
| `revert` | 이전 변경 사항 되돌리기 |

### 4.3 작성 기준

- 제목만 읽어도 변경 내용을 이해할 수 있도록 작성한다.
- Jira 이슈가 있는 작업은 유효한 이슈 키를 대문자로 정확하게 작성한다.
- 제목은 한글 또는 영어 중 팀이 이해하기 쉬운 언어를 사용하되, 하나의 메시지 안에서 불필요하게 혼용하지 않는다.
- 제목 끝에는 마침표를 붙이지 않는다.
- `수정`, `작업`, `업데이트`처럼 범위가 불명확한 표현만 사용하지 않는다.
- 서로 다른 목적의 변경은 가능한 한 별도 커밋으로 분리한다.
- 빌드가 실패하거나 실행할 수 없는 중간 상태의 커밋은 원격 저장소에 공유하지 않는다.

### 4.4 예시

```text
feat(S15P21C205-12): 기업명 자동완성 검색 기능 추가
fix(S15P21C205-24): 관계 그래프 노드 중복 렌더링 수정
docs(S15P21C205-31): 팀 협업 규칙 문서 작성
refactor(S15P21C205-38): 뉴스 전처리 로직 분리
test(S15P21C205-42): 관계 점수 계산 단위 테스트 추가
```

## 5. Push 규칙

- Push 전 현재 브랜치와 변경 파일을 확인한다.
- 최신 `dev`의 변경 사항을 반영하고 충돌을 해결한 뒤 Push한다.
- 프로젝트에서 정한 빌드, 정적 분석 및 테스트를 로컬에서 가능한 범위까지 수행한다.
- 본인이 작업한 브랜치에만 Push한다.
- `master`에는 직접 Push하지 않는다.
- `dev` 직접 Push는 코드나 실행 환경에 영향을 주지 않는 간단한 문서 작업에만 허용한다.
- 간단한 문서 작업은 오탈자 수정, 설명 보완, README 및 협업 문서 수정처럼 코드·빌드·배포·환경 설정을 변경하지 않는 작업을 의미한다.
- 문서와 함께 코드, 의존성, CI/CD, 빌드 또는 환경 설정이 변경되면 작업 브랜치와 Merge Request를 사용한다.
- 문서를 `dev`에 직접 Push하기 전 최신 `dev`를 반영하고, 팀원의 작업과 충돌하지 않는지 확인한다.
- 관련 Jira 이슈가 있는 문서 작업은 `docs(<issue-key>): <subject>` 형식으로 커밋한다. Jira 이슈가 없을 때만 `docs: <subject>` 형식을 사용한다.
- 공유 중인 브랜치에서는 `force push`를 금지한다.
- 불가피하게 커밋 이력을 변경해야 한다면 해당 브랜치 작업자 전원에게 먼저 알리고 동의를 얻는다.
- 불필요한 바이너리, 빌드 산출물, IDE 개인 설정 및 민감 정보가 포함되지 않았는지 확인한다.

## 6. Merge Request 규칙

### 6.1 생성 기준

- 일반 작업은 작업 브랜치에서 `dev`를 대상으로 Merge Request를 생성한다. Push 규칙에서 정의한 간단한 문서 작업은 예외로 한다.
- Merge Request 제목은 `<type>(<issue-key>): <subject>` 형식으로 작성한다.
- Jira 이슈가 있는 작업은 브랜치 이름, 커밋 메시지 및 Merge Request 제목에 동일한 이슈 키를 사용한다.
- 한 Merge Request에는 하나의 기능 또는 하나의 목적만 포함한다.
- 구현이 완료되고 기본 검증을 통과한 상태에서 리뷰를 요청한다.
- 작업 중 사전 공유가 필요하면 Draft Merge Request를 활용한다.

### 6.2 본문 필수 항목

Merge Request 본문에는 다음 내용을 포함한다.

```markdown
<!--
MR 제목 형식: feat(지라 코드): 기능명
예시: feat(S15P21C205-12): login
-->

## Part

- [ ] FE
- [ ] BE
- [ ] AI

<br/>

## 작업 내용

- 기능에서 어떤 부분이
- 구현되었는지 설명해 주세요.

<br/>

## 앞으로의 과제

- 다음에 진행할 작업을
- 작성해 주세요.

<br/>

## ➕ Jira 링크

- [S15P21C205-00](Jira 이슈 주소)

<br/>
```

- 작업에 해당하는 Part의 체크박스를 선택한다.
- `작업 내용`에는 이번 Merge Request에서 실제로 구현하거나 수정한 내용을 작성한다.
- `앞으로의 과제`에는 후속 작업, 미완료 사항 또는 다음 작업 계획을 작성한다. 해당 사항이 없으면 `없음`으로 표시한다.
- `Jira 링크`에는 실제 Jira 이슈 키와 해당 이슈의 전체 주소를 작성한다.
- 화면 변경이 포함된 경우 `작업 내용`에 스크린샷 또는 동작 영상을 첨부한다.
- API 변경이 포함된 경우 `작업 내용`에 요청·응답 형식과 영향받는 기능을 설명한다.

### 6.3 Jira 이슈 연결 규칙

- 일반적인 Merge Request에는 `[S15P21C205-00](Jira 이슈 주소)` 형식으로 관련 Jira 이슈 링크를 작성한다.
- `Closes`, `Fixes`, `Resolves`는 Jira 이슈를 완료 상태로 자동 전환하도록 설정된 표현이므로 팀이 완료 시점과 GitLab 연동 설정을 확인한 경우에만 사용한다.
- 하나의 Merge Request가 여러 Jira 이슈와 관련되면 관련된 이슈 링크를 모두 명시한다.
- 브랜치, 커밋 메시지, Merge Request에 작성한 Jira 이슈 키가 실제 작업 번호와 일치하는지 리뷰 요청 전에 확인한다.

### 6.4 리뷰 규칙

- 작성자는 본인이 변경한 내용을 먼저 자체 검토한다.
- 최소 1명 이상의 팀원에게 승인을 받은 후 Merge한다.
- 리뷰어는 코드의 정확성, 가독성, 테스트 여부, 보안 및 기존 기능에 미치는 영향을 확인한다.
- 수정이 필요한 의견과 선택적인 제안은 구분하여 작성한다.
- 작성자는 모든 리뷰 의견에 답변하거나 변경 사항을 반영한다.
- 해결되지 않은 필수 의견이 남아 있는 상태에서는 Merge하지 않는다.
- 긴급한 Merge가 필요한 경우에도 사유를 팀에 공유하고 사후 리뷰를 진행한다.

### 6.5 Merge 기준

- 충돌이 모두 해결되어야 한다.
- 필수 CI 작업이 성공해야 한다.
- 승인 기준을 충족해야 한다.
- Merge 직전에 대상 브랜치의 최신 변경 사항이 반영되었는지 확인한다.
- 기본 Merge 방식은 **Squash and Merge**로 하여 작업 브랜치의 커밋을 하나로 정리한다.
- Squash 커밋 메시지는 변경 목적이 명확하게 드러나도록 정리한다.
- Merge 완료 후 원격 작업 브랜치를 삭제한다.

## 7. 규칙 변경

- 본 문서는 팀 합의에 따라 변경할 수 있다.
- 규칙을 변경할 때는 변경 이유와 적용 시점을 팀에 공유한다.
- 기존 작업에 새 규칙을 소급 적용하기 어려운 경우 적용 범위를 별도로 합의한다.
