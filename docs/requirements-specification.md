# COSMOS 요구사항 명세서

## 1. 문서 개요

### 1.1 목적

본 문서는 뉴스·공시·주가 데이터를 기반으로 기업 간 관계를 분석하고 시각화하는 COSMOS 서비스가 충족해야 할 기능 및 품질 요구사항을 정의한다.

본 문서의 요구사항은 구현 진행 상황이 아닌 최종 서비스 기준을 나타낸다. 개발 일정, 담당자, 구현 상태와 작업 이력은 Jira 및 WBS에서 별도로 관리한다.

### 1.2 우선순위

| 우선순위 | 의미 |
| --- | --- |
| `MUST` | 서비스 제공을 위해 반드시 충족해야 하는 요구사항 |
| `SHOULD` | 핵심 사용자 경험과 운영 품질을 위해 우선적으로 충족해야 하는 요구사항 |
| `COULD` | 핵심 기능 완성 후 선택적으로 제공할 수 있는 확장 요구사항 |

## 2. 프로젝트 개요

COSMOS는 뉴스, 기업 공시 및 주가 데이터를 수집·분석하여 기업 간 협력·경쟁·공급·투자 관계를 도출하고, 이를 은하 형태의 3D 그래프로 제공하는 기업 관계 분석 서비스다.

기업은 행성 형태의 노드로 표현하고 기업 간 관계는 간선으로 표현한다. 사용자는 전체 기업 생태계 또는 특정 기업을 중심으로 관계망을 탐색하고, 관계 점수와 영향 방향, 분석 신뢰도 및 근거 뉴스를 확인할 수 있어야 한다.

### 2.1 프로젝트 목표

- 여러 출처에 분산된 기업 정보를 관계 중심으로 통합한다.
- 기업 간 복합 관계와 관계의 방향 및 강도를 분석한다.
- 기업 관계의 분석 근거를 함께 제공하여 결과의 설명 가능성을 확보한다.
- 기업 생태계를 직관적으로 탐색할 수 있는 3D 시각화를 제공한다.
- 원본 데이터를 보존하여 모델과 계산식 변경 시 분석 결과를 재현할 수 있도록 한다.
- 관심 기업을 중심으로 개인화된 기업 관계 탐색 경험을 제공한다.

### 2.2 주요 사용자

| 우선순위 | 사용자 유형 | 주요 목적 |
| --- | --- | --- |
| 1 | 투자 참고 정보를 탐색하는 사용자 | 기업 관계, 관련 뉴스 및 기업 상태 파악 |
| 2 | 기업과 산업 구조를 조사하는 사용자 | 기업 간 협력·경쟁·공급·투자 관계 탐색 |
| 3 | 취업·영업·기업 지원 목적으로 조사하는 사용자 | 특정 기업과 연관 기업의 생태계 파악 |
| 4 | 데이터 및 기업 관계를 분석하는 사용자 | 관계 점수, 근거와 기간별 변화 분석 |

### 2.3 서비스 제외 범위

- 실제 주식 주문 및 자동매매
- 특정 종목에 대한 매수·매도 추천
- 수익률을 보장하는 주가 전망
- 뉴스와 주가 변화 사이의 인과관계 단정
- 모든 국내외 기업에 대한 완전한 관계 정보 보장
- 공개 화면을 통한 공시 원문 재배포

## 3. 핵심 용어

| 용어 | 정의 |
| --- | --- |
| 기업 노드 | 3D 관계 지도에서 하나의 기업을 표현하는 객체 |
| 관계 간선 | 두 기업 사이의 관계를 표현하는 연결선 |
| 관계 유형 | 공급·투자(지분 포함)·협력·경쟁으로 구분한 기업 관계의 세부 분류 |
| 관계 점수 | 뉴스와 공시 분석 결과를 바탕으로 산출한 기업 관계의 강도 |
| 영향 방향 | 관계 또는 사건이 기업에 미치는 긍정·부정·중립·혼합 영향 |
| 분석 신뢰도 | 기업 식별 및 관계 분석 결과의 신뢰 수준을 나타내는 값 |
| 근거 데이터 | 기업 관계 분석의 근거가 된 문서와 근거 문장 |
| 관계 스냅샷 | 특정 기준 시각에 게시된 전체 기업 관계 분석 결과 |
| 내 은하 | 관심 기업과 직접 연결된 기업을 중심으로 구성한 개인화 관계 지도 |
| 뉴스·공시 가중치 | 화면에 표시할 관계 점수에서 뉴스와 공시 점수의 반영 비율 |

## 4. 전체 서비스 흐름

```text
뉴스 수집 ──→ 영속 Outbox ──→ Kafka ──→ HDFS
공시 수집 ────────────────────────────→ HDFS
주가 수집 ────────────────────────────→ HDFS
                                           ↓
                         기업 식별·관계·감성·영향 분석
                                           ↓
                         Spark 기간별 관계 점수 집계
                                           ↓
                         PostgreSQL 스냅샷 게시
                                           ↓
                         Spring Boot API 제공
                                           ↓
                         Web·Mobile 관계 지도 조회
```

## 5. 기능 요구사항

### 5.1 데이터 수집

| ID | 요구사항 | 우선순위 | 검증 기준 |
| --- | --- | --- | --- |
| COL-001 | 시스템은 국내외 뉴스 데이터를 정해진 주기로 수집해야 한다. | MUST | 설정된 주기에 따라 신규 뉴스와 수집 시각이 저장되는지 확인 |
| COL-002 | 시스템은 DART 및 SEC 기업 공시 데이터를 정해진 주기로 수집해야 한다. | MUST | 대상 기업의 신규 공시와 공시 식별자가 저장되는지 확인 |
| COL-003 | 시스템은 대상 기업의 일별 주가와 거래량 데이터를 수집해야 한다. | MUST | 기업별 OHLCV 데이터가 거래일 기준으로 저장되는지 확인 |
| COL-004 | 수집 데이터에는 출처, 원문 식별자 또는 URL, 발행 시각 및 수집 시각이 포함되어야 한다. | MUST | 필수 메타데이터 누락 여부 확인 |
| COL-005 | 동일한 문서가 반복 수집되어도 중복 저장과 중복 분석을 방지해야 한다. | MUST | 동일 문서를 재수집했을 때 논리 데이터가 중복 생성되지 않는지 확인 |
| COL-006 | 수집과 저장에 실패한 데이터는 재시도할 수 있어야 하며 반복 실패 데이터는 별도로 격리해야 한다. | MUST | 재시도, 격리 데이터 및 실패 원인 기록 확인 |
| COL-007 | 데이터 출처별 수집 성공·실패 여부와 수집량을 확인할 수 있어야 한다. | SHOULD | 출처별 실행 로그와 처리 건수 확인 |

### 5.2 기업 식별 및 AI 분석

| ID | 요구사항 | 우선순위 | 검증 기준 |
| --- | --- | --- | --- |
| AI-001 | 시스템은 뉴스와 공시 본문에서 기업명을 추출해야 한다. | MUST | 검증 데이터에서 기업명 추출 결과 확인 |
| AI-002 | 정식 명칭, 영문명, 약칭 및 종목명으로 표현된 기업을 동일한 기업 ID로 연결해야 한다. | MUST | 서로 다른 명칭이 동일 기업으로 연결되는지 확인 |
| AI-003 | 문맥을 분석하여 동명이인, 그룹명 및 일반 단어로 인한 기업 오탐을 줄여야 한다. | MUST | 주요 중의어와 오탐 검증 사례 확인 |
| AI-004 | 시스템은 기사에 함께 등장한 기업 쌍을 관계 분석 후보로 생성해야 한다. | MUST | 기사별 기업 쌍과 후보 문장 생성 결과 확인 |
| AI-005 | 시스템은 기업 쌍의 관계를 공급·투자(지분 포함)·협력·경쟁 유형으로 분류해야 한다. | MUST | 관계 유형별 분석 결과 생성 확인 |
| AI-006 | 하나의 기업 쌍에 서로 다른 관계 유형을 함께 부여할 수 있어야 한다. | MUST | 동일 기업 쌍에 복수 관계가 저장·조회되는지 확인 |
| AI-007 | 방향성이 있는 관계는 관계의 주체와 대상을 구분해야 한다. | MUST | 공급·투자 관계의 시작 기업과 대상 기업 확인 |
| AI-008 | 금융 뉴스가 관련 기업에 미치는 긍정·부정·중립 영향과 영향 강도를 분석해야 한다. | SHOULD | 동일 기사에 포함된 기업별 분석 결과 확인 |
| AI-009 | 분석 결과에는 모델 또는 분석기 버전, 신뢰도와 근거 문장을 포함해야 한다. | MUST | 분석 결과와 원문 근거 및 버전 연결 확인 |
| AI-010 | 신뢰도가 기준보다 낮거나 근거가 부족한 분석 결과를 제외하거나 별도로 표시해야 한다. | SHOULD | 신뢰도 기준 전후 노출 결과 확인 |
| AI-011 | 그래프 기반 모델을 통해 직접·간접 관계로 연결된 기업의 영향 방향과 강도를 분석할 수 있어야 한다. | COULD | 기준 기업과 다단계 연관 기업의 영향 분석 결과 확인 |

### 5.3 관계 점수 계산

| ID | 요구사항 | 우선순위 | 검증 기준 |
| --- | --- | --- | --- |
| REL-001 | 시스템은 기업 쌍과 관계 유형별로 문서 단위 관계 점수를 생성해야 한다. | MUST | 기업 쌍·관계 유형·문서별 점수 생성 확인 |
| REL-002 | 뉴스 점수와 공시 점수를 구분하여 계산하고 저장해야 한다. | MUST | 관계 결과에서 출처별 점수 조회 확인 |
| REL-003 | 중복 또는 재전송된 문서는 관계 근거 수와 점수에 반복 반영하지 않아야 한다. | MUST | 동일 문서 재처리 전후 결과 비교 |
| REL-004 | 최근 30일·1년·10년 기준 관계 점수를 각각 계산해야 한다. | MUST | 동일 관계의 기간별 점수 생성 확인 |
| REL-005 | 공급·투자(지분 포함)·협력·경쟁 관계 점수를 관계 유형별로 보존해야 한다. | MUST | 동일 기업 쌍의 유형별 관계 결과 조회 확인 |
| REL-006 | 관계 점수와 함께 영향 방향, 분석 신뢰도 및 근거 문서 수를 제공해야 한다. | MUST | 관계 상세 응답의 관련 값 확인 |
| REL-007 | 사용자가 뉴스와 공시의 반영 비율을 변경하면 AI 모델을 재실행하지 않고 표시 점수를 다시 계산해야 한다. | SHOULD | 가중치 변경 직후 표시 점수 변경 확인 |
| REL-008 | 관계 계산식과 분석 모델에 버전을 부여해야 한다. | MUST | 스냅샷과 분석 결과의 버전 정보 확인 |
| REL-009 | 모델 또는 계산식 변경 시 보존된 원본 데이터로 특정 기간이나 전체 관계를 다시 계산할 수 있어야 한다. | SHOULD | 재분석 결과와 실행 버전 생성 확인 |

### 5.4 3D 기업 관계 지도

| ID | 요구사항 | 우선순위 | 검증 기준 |
| --- | --- | --- | --- |
| MAP-001 | 시스템은 기업을 노드, 기업 관계를 간선으로 표현한 3D 관계 지도를 제공해야 한다. | MUST | 최신 스냅샷의 노드와 간선 렌더링 확인 |
| MAP-002 | 기업 노드는 산업, 기업 규모 및 기업 상태를 구분할 수 있도록 표현해야 한다. | SHOULD | 정의된 기준에 따른 노드의 시각적 차이 확인 |
| MAP-003 | 간선 색상으로 관계 유형을 구분해야 한다. | MUST | 관계 유형별 색상과 범례 일치 확인 |
| MAP-004 | 간선 굵기와 효과로 관계 강도를 표현해야 한다. | SHOULD | 점수 변화에 따른 간선 표현 차이 확인 |
| MAP-005 | 방향성이 있는 관계는 화살표 또는 흐름 효과로 방향을 표현해야 한다. | MUST | 공급·투자 관계의 방향 표시 확인 |
| MAP-006 | 사용자는 관계 지도를 확대·축소하고 회전할 수 있어야 한다. | MUST | 마우스 또는 터치 입력에 따른 카메라 조작 확인 |
| MAP-007 | 기업 노드 선택 시 해당 기업에 포커싱하고 기업 상세 정보를 표시해야 한다. | MUST | 노드 선택 후 카메라 이동과 상세 패널 표시 확인 |
| MAP-008 | 관계 간선 선택 시 관계 점수, 영향 방향, 신뢰도와 근거 뉴스를 표시해야 한다. | MUST | 간선 선택 후 관계 상세 패널 표시 확인 |
| MAP-009 | 기업명, 산업, 관계 유형과 최소 관계 점수에 따른 검색 또는 필터를 제공해야 한다. | SHOULD | 조건 적용 전후 노드·간선 결과 비교 |
| MAP-010 | 사용자는 특정 기업을 중심으로 최대 3단계의 연관 기업을 탐색할 수 있어야 한다. | MUST | 중심 기업 기준 단계별 관계망 조회 확인 |
| MAP-011 | 사용자는 두 기업 사이의 연결 경로를 확인할 수 있어야 한다. | SHOULD | 선택 기업 간 관계 경로와 경로별 관계 정보 확인 |
| MAP-012 | 선택 기간의 주가 등락률을 기업 노드의 높이 또는 보조 시각 요소로 표현할 수 있어야 한다. | COULD | 기간 변경에 따른 노드 상태 변화 확인 |

### 5.5 기업 상세

| ID | 요구사항 | 우선순위 | 검증 기준 |
| --- | --- | --- | --- |
| COM-001 | 기업명, 영문명, 종목코드, 시장, 산업과 기업 설명을 제공해야 한다. | MUST | 기업 상세 정보 표시 확인 |

## 8. 기술 및 배포 요구사항

### 8.1 서비스 구성

- 웹 클라이언트는 React와 TypeScript를 기반으로 구성한다.
- 3D 관계 지도는 Three.js와 React Three Fiber를 기반으로 구성한다.
- 사용자용 공개 API는 Spring Boot와 Java를 기반으로 제공한다.
- AI 추론 API가 필요한 기능은 Python과 FastAPI를 기반으로 구성한다.
- 모바일 애플리케이션은 React Native를 기반으로 구성한다.
- 회원·기업·뉴스·관계·커뮤니티 기능은 백엔드 내부에서 도메인별로 구분한다.
- 초기 서비스는 모든 도메인을 별도 서버로 분리하는 MSA 구성을 필수로 요구하지 않는다.

### 8.2 데이터 처리 구성

- 뉴스 이벤트의 비동기 전달과 재처리는 Kafka를 사용한다.
- 공시와 주가는 검증된 배치 파일을 HDFS에 게시한다.
- 원본과 분석 결과는 Hadoop HDFS에 보존한다.
- 대규모 정제·조인·관계 점수 집계는 Spark와 YARN을 사용한다.
- 분석 결과는 검증된 스냅샷 단위로 PostgreSQL에 게시한다.
- Spring Boot API는 요청 처리 중 HDFS 원본을 직접 조회하거나 Spark 작업을 실행하지 않는다.

### 8.3 배포 및 운영

- 웹 애플리케이션과 데이터 처리 작업의 배포 파이프라인을 분리한다.
- 프론트엔드, Spring Boot, PostgreSQL과 Redis는 Docker 기반 실행을 지원해야 한다.
- Hadoop과 Spark는 Linux 서버에 설치하고 YARN 기반 분산 실행을 지원해야 한다.
- Jenkins를 이용해 빌드·테스트·이미지 생성·배포 절차를 자동화해야 한다.
- 배포 실패 시 기존 정상 버전으로 복구할 수 있어야 한다.
- 인프라 설정과 배포 스크립트는 Git에서 버전 관리해야 한다.
- 현재 서버 규모에서는 Kubernetes를 필수 구성으로 사용하지 않는다.

## 9. AI 평가 요구사항

| 평가 대상 | 주요 지표 | 평가 기준 |
| --- | --- | --- |
| 기업명 추출 | Precision, Recall, F1-score | 정식명칭·약칭·동명이인과 오탐 사례 포함 |
| 기업 정규화 | Accuracy | 추출 명칭과 실제 기업 ID의 연결 정확도 |
| 관계 분류 | 유형별 Precision, Recall, F1-score | 협력·경쟁·공급·투자 유형과 다중 관계 포함 |
| 관계 방향 추출 | Accuracy | 공급·투자 관계의 주체와 대상 판별 |
| 기업별 감성·영향 분석 | Macro F1-score | 긍정·부정·중립 클래스 불균형 고려 |
| 관계 근거 추출 | 근거 문장 일치율 및 사용자 평가 | 관계를 직접 뒷받침하는 문장 여부 평가 |

- 학습·검증·테스트 데이터는 시간과 원천을 고려하여 분리해야 한다.
- 평가 데이터의 시장, 언어와 관계 유형별 분포를 기록해야 한다.
- 학습 데이터 이후에 발생한 정보가 평가 입력에 포함되지 않도록 데이터 누수를 방지해야 한다.
- 단순 규칙과 다수 클래스 등 기준 모델을 포함하여 모델 성능을 비교해야 한다.
- 모델 후보, 평가 결과와 최종 선정 근거를 문서화해야 한다.
